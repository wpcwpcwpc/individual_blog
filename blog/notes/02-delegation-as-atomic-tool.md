# 02 · 委派是可审计的原子工具调用，不是框架魔法

> 这是设计复盘，不是规范。行为要求见 `openspec/specs/team-member-execution`；编码约束见 `.codemaker/rules/`。行号截至 2026-11。

**一句话结论**：自编排 `delegate_batch`——委派是带批次屏障的原子工具调用，leader 的决策永远基于全部成员的真实终态。

## 场景

多 Agent 系统里最核心的动作是委派：leader 把子任务交给成员，收回结果，再决策。框架给了 `Team` 一个原生 delegate 能力，我们的第一版也确实想直接用它。把它的行为边界摸了一遍之后，我们放弃了，因为它缺了四样编排系统绕不开的东西：

1. **真实终态**。委派返回时，成员可能还没跑完——拿到的是「发起结果」而不是「执行结果」。leader 基于半成品决策，等于把竞态引进了决策链。
2. **并发硬限**。没有机制限制同时在跑的成员数。leader 在同一轮里并发发起 N 个委派，框架层面拦不住，TPM 和下游系统跟着遭殃。
3. **成员级 Stop**。跑飞的成员停不下来——只能整轮终止，陪葬的还有其他正常成员。
4. **实时成员事件**。过程黑盒：时间线上只有成员最后吐的那段文本，中间在查什么、卡在哪里，一概不可见。对调试和安全审计都是灾难。

四条里任何一条都能忍，四条叠加就是「编排不可控、过程不可见、出事救不了」。

## 我们的方案

把委派从框架特性降级成一个**普通工具调用**：leader 的工具清单里多一个 `delegate_batch(tasks)`（`team_delegate.py:632`），委派语义由我们自己实现。`Team(members=[])` 构造——框架的 Team 只承载 leader 自己，成员由工具在运行期创建和驱动。

`delegate_batch` 的执行链是三层结构：

- **批次层**。`_run_batch`（`team_delegate.py:579`）持有进程内批次锁——同一个会话同时只有一个批次在执行。批内任务分发给 `_run_one`。
- **尝试层**。`_run_one`（`:417`）先从 permit 池拿许可。permit 池是个 `threading.BoundedSemaphore`（`team_execution.py:51`），同时覆盖线程与协程两种执行形态；额度 `1 if serial else max_parallel_members`（默认 2，`team_session.py:265`）。拿到许可后 `member_factory` 创建独立 Agent，`_execute_member`（`team_delegate.py:335`）流式驱动成员，每个事件经归一化后实时发出——这就是时间线上成员卡的来源（观测细节见 05 篇）。
- **屏障层**。批次屏障是整个设计的枢纽：**所有尝试进入真实终态之后，工具才返回**。leader 调 `delegate_batch` 得到的结果里，每个任务要么有终态产出、要么有明确的失败原因。没有「还在跑」这种中间态泄漏给决策层。

在这之上是**原子门禁**。leader 的所有工具都标 `requires_confirmation=True`：工具真正执行前，运行进入暂停，gate 按 `tool_call_id` 对整批调用做审查。同一轮里如果混了「委派 + 业务工具」、或者出现多个 `delegate_batch`，整批拒绝、零副作用——不会有半批被执行。内部门禁的决议不产生公开的用户审批，也绝不自动批准真实的审批项，两条都是防止门禁变成橡皮图章。

成员级 Stop 的语义也定在这层：`_run_one` 捕获单项取消后不上抛（`team_delegate.py:468-488`），被停的成员标记终止，批次继续收齐其余成员的终态；只有父级（整轮）取消才向上传播。「停一个不废一批」是编排可用性的底线。

## 为什么这样选

**弃「Team 原生 delegate」**：上面四缺口。补充一句实测观感——并发无上限叠加「返回即继续」，leader 会在同轮 gather 出一串委派，我们见过 4 个成员同时把下游查询接口打到限流。框架特性的问题在于你无法给它补洞，只能绕开。

**弃「分段 Team run」**：另一个思路是保留框架委派，把一轮拆成多段运行——委派前暂停一次、结果回来再开一段。评估后放弃：运行记录被拆散、hooks 与 summary 重复触发、前端时间线要靠拼接假装连续。修这三个问题的成本超过自建编排。

**弃「提示词约束」**：「同一轮只允许调用一次 delegate_batch」这类规则当然写进了指令，但我们从不把正确性押在指令上——LLM 偶尔不听，而约束必须是机制。指令负责降低违规概率，门禁负责违规时归零副作用，两者缺一不可。

**为什么「原子」值得强调**：委派一旦混批执行，「部分成员已经跑了、审批却拒了另一半」的状态几乎无法向用户解释，回滚也无从谈起。整批生效或整批拒绝，让委派拥有数据库事务的直观语义——这是 leader 敢于放心发起大批次的前提。

## 代价与边界

- **吞吐上限**。批次锁意味着同会话批次串行，并行度只存在于批内 permit 额度（默认 2）。吞吐要提，调额度的同时要评估 TPM 与下游承载——这是设计好的旋钮，但不是免费的。
- **每轮都过门禁**。全自动场景需要另配 auto 审查规则，否则人审交互成本很高。我们把「门禁可自动化的规则面」留成了扩展点，而不是做成开关一放了之。
- **屏障等待**。批内最快成员要等最慢成员，长尾任务拖整批返回。任务是切给成员的粒度，切得越粗长尾越疼——委派设计的另一面是任务拆分纪律。
- **没有断点续跑**。成员失败后重派是从零开始的新 run，不假装支持工具调用级续跑。要续跑语义，得在任务拆分层做（把大任务切成可独立重试的小任务），而不是在委派层做。

## 可复用结论清单

1. 委派做成 leader 的普通工具调用，编排语义自己实现——框架的原生委派能力通常缺少终态、限流、单点停止、过程事件这四块拼图。
2. 批次屏障是决策正确性的根基：工具返回前，所有子任务必须有真实终态。
3. 并发上限用信号量实现且要同时覆盖线程与协程形态，别赌运行环境只有一种。
4. 门禁按「整批」审查与拒绝：混合调用零副作用，比事后回滚便宜一百倍。
5. 单点停止的语义要在设计期定死：停成员不废批次，父级取消才向上传播。
6. 指令负责概率，机制负责兜底——任何「模型应该不会这么做」的想法都不是防线。
7. 不做断点续跑就明说，把续跑需求推给任务拆分层，别在委派层造半吊子恢复。
