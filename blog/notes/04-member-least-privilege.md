# 04 · 成员是最小权限的：只读三件套与结果卸载

> 这是设计复盘，不是规范。行为要求见 `openspec/specs/team-member-execution`；编码约束见 `.codemaker/rules/`。行号截至 2026-11。

**一句话结论**：成员权限每多一项，治理成本翻一倍；上下文边界是安全的另一半——大结果走指针，不走值。

## 场景

设计成员角色时，最省事的方案摆在面前：把 leader 的定义复制一份，改改指令——成员自动继承全套工具（`file_edit`、`bash`、MCP、Skill）、历史与记忆，跑完把结果全文塞回给 leader。

这条路有两个断崖：

- **权限面失控**。成员是 leader 发起的、成批创建的、并发运行的。继承的每一项写能力（改文件、执行命令、调外部系统）都被放大 N 倍，而且发生在审查视野之外——门禁审的是 leader 的调用，成员在里面干了什么，审批者根本看不见。
- **上下文爆炸**。成员是调查机器，产出动辄上万字。几个成员的报告全文回到 leader 上下文，当轮 token 冲上天花板，后续每一轮还背着这些字节跑完全程——这在单 Agent 时代我们就付过学费（总册 K2：可变状态全量进消息，前缀缓存全废）。

所以成员的设计要同时回答两个问题：**它能做什么（权限边界），它能带回什么（上下文边界）**。

## 我们的方案

**权限边界：只读三件套。** `build_member_definition`（`team_member.py:260`）构造的成员只有 `file_read`、`grep`、`glob_search` 三个工具；MCP 工具、Skill 工具、记忆、历史注入全部显式关闭。能准入的成员角色也走白名单（`ADMITTED_MEMBER_ROLES`，`team_leader.py:25`），首期只有 `general-agent` 一个——不是从全量注册表自动生成候选。分工因此非常清楚：**成员负责调查，leader 负责动手**；一切写操作与外部交互都回到 leader 的门禁之下。

**成员会话独立。** 每个成员跑在独立会话 `{sid}__member__{role}` 里：上下文与记忆物理隔离，会话删除时级联清理，留痕有上限——每个成员会话最多保留 20 条 run（`prune_member_session_runs`），超限裁剪最旧的；leader 注入成员摘要时只取最近 5 条。成员的可见性因此是有界的、可治理的。

独立会话有一个不便宜但必须付的代价：Agno 的会话存储是「读全量 → append → 写全量」的语义，天然 last-write-wins。成员并行保存时，后写的会覆盖先写的——**丢 run 不是 bug，是存储语义**。对策是 `_repair_member_run`（`team_delegate.py:262`）：批次结束后按账本比对，缺的 run 在进程内持久化锁下串行补写，`upsert_run` 幂等保证补写不产生重复。

**上下文边界：结果卸载。** 成员产出超过 1500 字符就信封化：全文写进 `{data_dir}/team_results/{sid}/`，leader 拿到的是 `result_id`、字符数和一小段预览。要看全文，leader 调 `read_result`（`team_session.py:222`）分窗回读——默认窗 4000、单次上限 8000 字符。信封结构升级时保持向外兼容（新增结构化字段，不删旧字段），leader 侧不用重新学习怎么读结果。安全上，`result_id` 与会话绑定，只允许读本会话目录，跨目录与路径穿越直接拒绝；会话删除时整目录剪除，不搞条目级 LRU——目录的生灭跟会话一致，就没有孤儿。

## 为什么这样选

**弃「按任务动态开权」**：「这个任务是只读调查，所以临时开 grep」听起来很合理，但它把安全边界从静态白名单变成运行时变量——审计者要还原「当时为什么开了这个权限」，几乎不可能。权限边界必须是创建期定死的静态事实。

**弃「共享会话」**：成员与 leader 共享上下文，省了结果传递，换来的是：成员的中间推理污染 leader 的历史、记忆互相覆盖、删除无法级联。隔离的收益（可治理）大于传递的便利（反正有信封机制）。

**弃「结果全量进 prompt」**：实测多成员各回一份万字报告时，leader 当轮 token 飙升、TPM 直接 429，而且这些字节在后续每轮都重复计费。信封加预览把「带回什么」的决策权交还 leader——它觉得预览够了就不必翻全文。

**弃「结果存 Mongo」**：成员消息本身已经持久化，结果再存一份就是双写，还要给清理加钩子。文件目录方案没有任何新依赖，生灭跟会话严格同步，排查时人也能直接 `ls`。

**弃「`read_result` 限流抛异常」**：限流触发时返回一段引导文案（「稍后再试 / 先处理已有结果」）而不是错误堆栈。模型拿到错误时倾向于换路线硬闯，拿到引导时倾向于照做——把控制权交回模型，比报错更能自愈。

## 代价与边界

- **成员不能写文件、不能执行命令**。需要落盘或执行的场景，只能回到 leader 串行完成。这是刻意的：调查可以并行，动手必须过门禁。
- **补写锁是进程内的**。当前部署形态下单进程成立；如果未来多进程部署，last-write-wins 的补写要重新设计。这是一个如实记录的边界，不是已解决的问题。
- **留痕上限 20**。超长调查的早期留痕会被裁剪，成员详情回看有界。对调试是轻微损失，对存储是确定收益。
- **分窗回读增加回合数**。leader 读一份长报告要翻几页，每页一个工具调用一个回合。用回合数换 token 是这笔交易的本质，任务粒度设计得好（成员产出短而准），交易才划算。

## 可复用结论清单

1. 成员权限白名单在创建期定死，准入角色也走白名单——安全边界不做成运行时变量。
2. 「成员调查、leader 动手」是可靠的分工默认值：并行化只读部分，串行化一切写与外部交互。
3. 成员会话独立：隔离的不是礼貌，是删除级联与留痕治理的可能性。
4. 并行写同一存储时先查语义——「读全量写全量」型存储必然 last-write-wins，补写账本要在设计里有位置。
5. 大结果走指针：`result_id` + 预览 + 分窗回读，把「要不要全文」留给 leader 决策。
6. 对模型限流，返回引导文案而非异常——自愈效率完全不同。
7. 结果存储的生灭周期跟宿主对象（会话）严格一致，就不需要单独的垃圾回收设计。
