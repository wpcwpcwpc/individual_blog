## Context

- 需求背景见 `proposal.md`：把两个内部项目改造成**可运行的公开版本**，作为可被阅读、也可被运行验证的工程实物
- 地基由 `add-personal-site` 提供（Astro 静态站点、排版规范、脱敏闸门、图表管线、部署链路）
- 先例：`add-claudecode-source-series` 的 `import-series.mjs` 建立了"一次性导入 + 脚本固化边界 + 源不进仓 + 产物过闸门"的模式；本变更沿用同一精神，但输入是源码，且必须改造到可运行

探索与实施阶段实测到的关键事实（决定了本设计的所有取舍）：

1. **业务密度不按目录分布**。同一目录内可能同时存在"零改动的通用文件"与"纯业务文件"；实测某中间件目录 23 个文件里只有 5 个可零改动使用。**判定必须落在文件粒度。**
2. **MIXED 桶的性质在目录间相反**。一侧可能是"90% 业务规则 + 10% 骨架"（救回来只剩空壳，不值得救），另一侧是"90% 骨架 + 少量内部事实"（每个只切几行）。**按比例或按目录外推必然出错。**
3. **选择式搬运存在静默遗漏缺陷**。逐文件挑选复制时，漏掉一个该保留的文件，结果是它**默认消失且无机制可发现**（闸门只能抓"多了不该有的"）。反之"全量 + 删减"的遗漏方向是"多了"，会被闸门当场抓住。**对数百文件、跨会话、反复确认的工程，错误必须朝可检测的方向偏。**
4. **词表抓不到语义**。实施中发现三类词表未收录的内部标识（内部网关名、雇主名、内部变更名引用）与一类误报（盘符路径正则误吃源码里的转义换行）。闸门是必要不充分的。
5. **体积陷阱**：源目录含构建产物与嵌入运行时（单目录上千个源文件）、缓存目录、以及被版本控制的本地配置文件（含真实凭证位与内网地址）。全量拷贝必须带排除规则。
6. **最大单文件是业务与机制的混合体**：一个流式事件适配层，表面是框架事件到前端事件契约的规范化，内里扎着业务语义分支，需要单独立项。

## Goals / Non-Goals

**Goals:**

- 把一个多 Agent 系统的通用能力改造成**可运行**的公开版本：本地能起服务、能建会话、能走通对话与流式输出
- 全程可审计：每一批的判定、依据、状态都有记录，跨会话可续
- 减法优先：能删就删，替换只用在"不替换则跑不起来"的地方
- 零暴露窗口：改造期间内容不进 git 历史；提交是一次显式动作，不是默认结果
- 与既有展示层互补：镜像是"实物"，项目页与文章是"叙述"

**Non-Goals:**

- 功能对齐原内部系统（业务能力不回填，被删除的功能就是删除）
- 生产可用性（不做部署、并发压测、监控告警；"本地跑通"即达标）
- 多租户、权限体系的生产实现（原权限闸门可保留为机制展示；认证以最小可用为准）
- 增量同步（不做子模块、不做远端引用、不做定期重导）
- 阶段一就把镜像区接入站点页面（文件树/代码浏览另开变更）
- 把镜像区做成通用框架并开源运营（不接 PR、不建社区）

## Decisions

### D1 判定线：三条都通过才算通用

| 线 | 判据 | 反例特征 |
|---|---|---|
| 依赖线 | 不依赖任何组织专有系统（内部平台、内部网关、内部存储、内部通讯） | 常量里写着内部服务地址、内部 SDK 导入 |
| 领域线 | 不理解业务专有名词（业务实体、业务编号、业务产物格式） | 出现业务词、业务 ID 正则、业务产物模板 |
| 可迁移线 | 换一个行业仍能直接使用 | 只有放进原业务语境才成立 |

三条线画在**文件**上，不画在目录上。目录名不具备判定力（实测两者可以完全相反）。

### D2 四级处置：减法优先、替换受控

| 判定 | 动作 | 验收标准 |
|---|---|---|
| `KEEP` | 零改动 | 逐字节等同源文件（除来源声明头） |
| `CUT` | 整块删除 | 文件不出现在镜像区 |
| `MIXED` | 机制保留、内容行级删除 | 删除行可逐条列举 |
| `REPLACE` | 内部依赖替换为公开实现或本地 mock | 替换点可逐条列举；替换物自身过闸门 |

**减法优先**：能用删除解决的，MUST NOT 用替换。`REPLACE` 仅用于"不替换则无法启动"的位置（内部网关、内部存储、内部协作系统、内部设备平台、内部认证）。

**替换物同样受约束**：
- MUST NOT 硬编码任何内部事实（地址、凭证、数据模型名、业务词）
- 配置 MUST 经环境变量注入，并附 `.env.example`（值全为占位）
- MUST NOT 以"我写的"为由豁免闸门

**明确禁止**：伪造能力展示（把 mock 包装成真实能力）、伪造指标、为了让演示好看而写死数据。

### D3 MIXED 与 REPLACE 都必须逐文件列清单后再拍

禁止按目录或按比例外推。每个待判文件先给出：**它在干什么**、**业务点在哪**、**处置量**。作者据此逐文件拍板。

配套推论：当某文件的"机制与价值不可分离"时（价值就长在被删除的业务规则里），判定降级为 `CUT`——保留空壳不如不留。

### D4 落位与改造期隔离

- 顶层 `mirror/`，下按项目 slug 分目录（`mirror/qa-agent/`、`mirror/qa-agent-ui/`）
- **改造期 `mirror/` MUST 处于 gitignore 之下**：这是"最后才提交"的机械保障，防止任何形式的 `git add -A` 把内部内容一次性纳入
- 揭幕（移除 gitignore 行）是**单一显式动作**，只在全量终审通过后执行
- 镜像区 MUST NOT 被站点页面引用（另开变更才行）

### D5 可运行化目标与验收范围

- 目标形态：**本地可启动、核心链路可走通**
- 后端：可安装依赖并启动 API 服务，健康检查通过
- 前端：可安装依赖并启动开发服务器，界面可用
- 对话链路：可创建会话、发送消息、收到流式输出（对接公开供应商的 OpenAI 兼容 API）
- 交互链路：至少走通"中断审核"这一条（它是本项目最有辨识度的机制）

**验收范围（已钉死）**。作者确认的目标形态是"通用的 Agent 前后端 Web 服务"，保留面按能力列出：

| 能力 | 纳入 | 说明 |
|---|---|---|
| 会话管理 | ✅ | 创建、列表、状态、历史分页 |
| 持久化 | ✅ | 会话与运行记录落库，重启可恢复 |
| 人机协同（HITL） | ✅ | 分级审批：命令级预览与修改、结果级验收 |
| 技能与工具 | ✅ | 技能加载、工具注册、MCP 接入 |
| 多 Agent 协作 | ✅ | 编排者 / 工作者模型 |
| 上下文治理 | ✅ | 用量统计、压缩、续跑 |

**明确排除**（列入即视为范围扩张，需显式改本设计）：

- 面向特定行业的业务页面、业务实体建模、业务产物模板
- 追踪面板与评测体系（可后续另开变更）
- 生产可用性（部署、并发、监控、安全加固）

范围一旦被"顺便把那个功能也恢复一下"扩张，工作量会失控。

### D6 全量搬迁工作法（先整体、再删减）

1. **全量拷贝**：两个项目源码整体落入 `mirror/<slug>/`，带排除规则（见 D7）；对**目标已存在**的文件跳过，避免覆盖已脱敏内容
2. **应用已有判定**：把已完成的批次的 `CUT` 文件删除、`MIXED` 编辑落到副本上
3. **逐目录推进**：剩余目录按批次判定 → 拍板 → 处置 → 记账
4. **补齐可运行性**：`REPLACE` 替换、配置模板、启动说明
5. **本地验证**：按 D5 的验收范围逐条走通
6. **揭幕与提交**：终审 → 移除 gitignore → 提交

理由：全量法把"遗漏"从静默变为可检测（事实 3），且对深层嵌套的前端目录，"删"比"挑"省事得多。

### D7 排除清单（拷贝时即生效）

MUST NOT 进入镜像区：本地配置文件与其备份（含真实凭证位）、构建产物、嵌入运行时、依赖安装目录、缓存目录、二进制与媒体文件、版本控制内部目录。

理由：这些内容要么是体积灾难（嵌入运行时单目录上千文件），要么是最高危的泄露源头（本地配置含内网地址与凭证位）。

### D8 清单与公开文档分离

| 内容 | 载体 | 是否入库 |
|---|---|---|
| 逐文件真实处置表（含真实文件名、业务点定位） | `SANITIZE-LIST.local.md` | **否**（gitignore） |
| 泛化类别与批次状态 | `openspec/` 变更文档 + `mirror/README.md` | 是 |
| 禁出词表 | 本地文件 + CI secret（沿用既有机制） | **否** |

理由：把"内部文件名 → 处置"的对照关系公开，等于免费提供内部模块地图。

### D9 闸门扩展而非新闸门

在既有 `sanitize-check.mjs` 上扩展：新增扫描根（镜像区）、扩展名集合扩至源码类型、支持无扩展名白名单、显式声明排除规则。词表来源、缺失即失败、打码输出、豁免告警**全部沿用，不放宽**。

改造期闸门会持续失败且这是预期：站点预览走 `astro` 直调，不跑 `npm run build` 全链路。

### D10 提交与回滚

- 改造期不提交镜像区（D4 的 gitignore 保障）
- 揭幕与提交是单一动作，前置条件：全量闸门通过 + 人工终审通过 + 本地验收通过 + 体量核对通过
- 回滚：揭幕前随时可弃（工作树内删除即可，无历史痕迹）；揭幕后误入的部分只能后续修正，**故终审为强制关卡**

### D11 源侧零留痕

- 不做子模块、不做远端引用、不做定期重导
- 源仓库 MUST NOT 因本次搬运产生任何改动
- 源目录真实路径 MUST NOT 出现在仓库任何文件（含注释、脚本、文档、提交信息）

### D12 认证替换形态：公开 OAuth

内部认证是组织专有的 OpenID 单点登录，属于"不替换则无法启动"的位置，判定为 `REPLACE`，替换物为公开 OAuth（GitHub）。

实测成本低于预期（证据）：

- 角色模型（`internal` / `normal` 二分）的消费者共 **3 处**：评测路由（随该路由一并 `CUT`）与追踪接口 2 处。追踪接口的用途是"按用户隔离数据"，属通用机制 → 改造方式为**删除角色判断、一律强制按用户隔离**（减法优先；公开版不需要特权角色，且 fail-closed 更安全）。于是整个角色模型可整体删除，不需要替代实现
- 员工目录校验函数零调用方（死代码）→ 跨库的员工目录引用可一并 `CUT`
- 后端身份依赖点仅 7 处，且全部只要"当前用户标识"，不要角色
- 前端认证状态容器与供应商无关（只存用户标识 + 状态），可原样复用

**教训（已两次踩到）**：角色的真实消费者数量被低估两次——先按"评测路由独占"推断，实为 3 处；业务 Agent 数量被低估一次——按"引入了中间件的文件"推断，实为 17 个。凡"某机制只有 N 个消费者"或"某类文件有 N 个"的论断，MUST 用全仓检索核实，MUST NOT 由局部引用或代表性子集推断。

替换契约：会话内只保存**本系统用户标识**，不保存第三方凭证；第三方令牌仅用于一次性换取用户资料。

### D13 删减顺序：业务 Agent 先行，孤儿机械回收

实测装配层（`agents/base.py`）只引入 4 个通用中间件；**全部业务中间件与业务工具都由业务 Agent 自行引入**。

推论：删减必须**从业务 Agent 开始**，而不是从中间件或工具开始。业务 Agent 删除后，"哪些中间件与工具成了孤儿"变为**零引用可机械判定**的事实，无需逐个判断业务属性。

若顺序颠倒（先删中间件），会出现"删了仍有引用"的启动失败，以及"看着像业务其实通用"的误删。**顺序即安全性。**

### D14 内部事实清零点：源码默认值 + 本地配置

实测：内部地址与内部系统名**不只存在于被版本控制忽略的本地配置里，也作为默认值写在源码中**（数据库连接串、协作系统回调地址、对象存储端点与桶名、报表回填地址）。

推论：仅删除本地配置文件**不充分**。清零点 MUST 覆盖两处：

1. 本地配置文件（含其备份）→ 整体 `CUT`，改为全占位的示例模板
2. 源码默认值 → 逐条清空或改为公开占位

验收方式为按内部主机名与内部系统名的全仓检索零命中，而非"检查过配置文件"。

### D15 会话签名密钥不得有默认值

实测：会话签名密钥带一个固定的常量默认值。在单一登录出口（组织单点登录）之后，这不是有效攻击面；**替换为公开 OAuth 后，它成为唯一一道防线**——密钥可预测等于会话可伪造。

契约：该配置 MUST NOT 提供默认值；缺失时服务 MUST 拒绝启动并给出明确提示。此为 D12 的前置条件。

## Risks / Trade-offs

- **[R1] 语义泄露（词表判不了"这段逻辑本身在描述业务"）** → 逐文件人工确认 + 闸门兜底；终审标准为"假设雇主会读到这一行"
- **[R2] 不可逆公开** → 改造期 gitignore 隔离 + 揭幕前置四道核对；提交集中一次
- **[R3] 生成物或本地配置误入** → 排除清单在拷贝时生效 + 体量核对（数量级异常即视为信号）
- **[R4] 体量失控** → 排除清单；仍过大则对业务耦合深的目录只保留代表性子集
- **[R5] 与既有决策冲突**（原 Non-Goals 明确排除可运行） → 本变更显式替换该约束，边界写进规格，不得再扩张
- **[R6] 镜像区被站点误引用** → 不在构建输入集；引用需另开变更
- **[R7] 本地清单丢失（不在版本控制）** → 公开侧登记批次状态；清单用固定模板
- **[R8] 为可运行性补实现导致脱敏失控** → 替换物同样过闸门（D2）；新增代码单独成为一批「复核对象」，不给"新写的"豁免
- **[R9] 巨型混合文件拖垮单批** → 单独立项深读
- **[R10] 判定口径漂移** → 判定线与四级动作写进规格；每批必须给依据
- **[R11] 可运行范围膨胀（"顺便把这个功能也恢复"）** → 验收范围在动工前钉死（D5），新增范围需显式改本设计
- **[R12] 运行期泄露**（启动日志打印内部路径与地址、错误信息带内部主机名） → 替换层必须把配置来源与错误信息通用化；本地验证时检查启动与报错输出
- **[R13] 依赖可安装性（内部源、私有包）** → 依赖清单逐项核对，内部源替换为公开可得版本；无法公开替代的依赖必须随模块一并 `CUT`
- **[R14] "能启动"被误读为"生产可用"** → `mirror/README.md` 明确声明：本地可跑通、不保证生产可用、不使用任何内部资源
- **[R15] 公开 OAuth 的可运行摩擦** → 第三方 OAuth 需要在提供方注册应用并配置回调地址；若不额外说明，克隆者无法直接跑起来。README MUST 给出注册步骤；回调地址以本地回环为准（提供方允许），不引入公网依赖
- **[R16] 删减顺序颠倒导致误删或启动失败** → 业务 Agent 先行（D13）；孤儿以零引用机械判定，不按业务属性人工判断
- **[R17] 全量拷贝覆盖既有处置成果** → 已实际发生一次（拷贝回滚了此前 4 批已脱敏内容）。后续任何重拷贝 MUST 先核对目标是否已被处置；处置脚本 MUST 可重跑且幂等

## Migration Plan

1. 闸门扩展落地并自测（已完成）
2. 全量拷贝：`mirror/qa-agent/`、`mirror/qa-agent-ui/`，带排除规则；`mirror/` 入 gitignore
   - **已由作者手工执行，且覆盖了此前的 4 批处置成果**（见 R17）。因此第 3 步不是"应用已完成批次"，而是"连同此前批次一并对原始副本重做处置"
3. 首轮删减（顺序即安全性，见 D13）：业务 Agent → 业务路由 → 孤儿回收 → 内部地址清零 → 非代码清理
4. 逐目录推进剩余细部核对（判定 → 拍板 → 处置 → 记账）
5. 配置与存储通用化：内部地址零点（D14）、会话签名密钥（D15）
6. 认证替换：公开 OAuth（D12）
7. 模型底座替换：公开供应商的 OpenAI 兼容客户端
8. 前端批次：业务页面连同其专属组件、状态库、接口模块整体 `CUT`
9. 本地验证：后端启动 + 前端启动 + 对话链路 + 中断审核链路
10. 全量复核：闸门、体量、人工终审、零留痕、引用核对
11. 揭幕：移除 gitignore 行，提交（单次）
