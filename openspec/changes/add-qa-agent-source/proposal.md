## Why

站点已能证明"我做过什么"（项目页 + 6 篇文章 + 11 张重绘图 + deck），但证明不了"我怎么写的"——现有展示层全是内容转述，读者看不到可验证的工程产物。

手上两个内部项目（一个多 Agent 后端平台、一个配套前端控制台）是唯一能补上这一环的实物。目标是把它做成**能跑起来的公开版本**：读者能克隆、能起服务、能对话，也能读到实现。为此必须解决三件事：

- **它是内部系统**：承载业务资产、内部系统标识、内网事实与个人标识。要公开的不只是"删掉敏感词"，而是把内部依赖替换成公开可得的实现
- **搬运是不可逆的公开动作**：一旦提交并推送，内容进入 git 历史与 CI 日志，泄露无法回收。所以"最后才提交"必须是机械保障，不是自觉
- **现有闸门覆盖不到源码**：`sanitize-check.mjs` 只扫站点内容、图表源、deck 与 `openspec/`，扩展名限定在 `.astro/.ts/.md/...`。源码进了仓库而闸门看不见，等于没有脱敏

## What Changes

- **全量搬迁阶段**：两个内部项目的源码先整体落入 `mirror/`，该目录在整个改造期 **MUST 处于 gitignore 之下**（揭幕前不可提交），由此把"暴露窗口"压到零
- **四级处置**：`KEEP`（零改动）/ `CUT`（整块删除）/ `MIXED`（机制保留、内容行级删除）/ `REPLACE`（内部集成依赖替换为公开实现或本地 mock）
  - 前三级为减法；`REPLACE` 是为"可运行"引入的**受控加法**：允许新增适配层、替换实现、补配置模板与启动说明
  - **新增代码与新增配置同样 MUST 过脱敏闸门**，不得以"这是新写的"为由放行
- **可运行化目标**：后端可本地启动、前端可本地起界面、LLM 对话链路可用（对接公开供应商的 OpenAI 兼容 API），核心交互路径可走通
- **排除清单**：`.env` 及一切本地配置文件与备份、构建产物、嵌入运行时、依赖目录、缓存 —— MUST NOT 进入镜像区
- **闸门扩展**：`sanitize-check.mjs` 扫描面新增镜像区与源码扩展名（含无扩展名白名单），并显式声明排除规则
- **揭幕与提交**：改造完成、本地验证通过、全量终审通过后，才移除 `mirror/` 的 gitignore 并提交；**BREAKING**（对既有决策）：原"阶段一不求可运行、只删不创"的约束在本变更内被替换
- **逐文件处置清单与公开文档分离**：真实文件名的处置表只落本地 gitignore 文件（与 `GLOSSARY.local.md` 同构）
- **源侧零留痕**：源仓库 MUST NOT 因本次搬运产生任何改动；源路径 MUST NOT 出现在仓库任何文件中

## Capabilities

### New Capabilities

- `source-curation`: 处置判定——通用/业务的判定准则（依赖线 + 领域线 + 可迁移性），四级处置的动作与边界（减法优先、替换受控），逐目录批次的确认循环与状态登记
- `source-sanitization`: 源码级脱敏——内部事实类别（内网地址与端口、凭证与密钥、个人标识、内部产品与平台名、业务专有名词、业务数据模型），删除/泛化/占位/替换的规则，**新增代码同样受约束**，清单与公开文档的分离约定
- `source-mirror`: 镜像区形态——落位与结构、改造期不入库（gitignore 守护）与揭幕流程、排除清单、批次元数据、只读与否的原则
- `source-runnable`: 可运行化——替换契约（哪些内部依赖以何种方式替换）、配置与密钥的通用化（环境变量 + 示例文件，无真实值）、本地启动路径与验收范围、运行期不得暴露内部事实

### Modified Capabilities

- `sanitization-gate`: 扫描面从"站点内容与图表"扩展到"站点内容 + 源码镜像"，扩展名集合扩至源码类型并支持无扩展名文件，新增排除规则（构建产物、依赖目录、缓存、嵌入运行时），且扫描面扩张 MUST NOT 带来任何免扫描例外

## Impact

- 新增目录：`mirror/qa-agent/`、`mirror/qa-agent-ui/`（改造期 gitignore，揭幕时放行）
- 脚本：`scripts/sanitize-check.mjs`（扫描面、扩展名、排除规则）
- 公开文档：`GLOSSARY.md`（源码类边界与登记）、`RELEASE-CHECKLIST.md`（源码镜像核对项）、`mirror/README.md`（形态声明与批次台账）
- 本地不入库：`SANITIZE-LIST.local.md`（逐文件处置表）
- 不受与内容、`/projects/<slug>` 契约、deck、PDF、简历页、图表管线机制
- 体量：镜像区将引入数百个后端文件 + 数百个前端文件；构建产物与嵌入运行时必须显式排除，否则仓库体积失控
- 改造期约束：闸门在镜像区未清理干净前会持续失败，故站点预览走 `astro` 直调，不走 `npm run build` 全链路
- 风险：可运行化引入的新增代码需要额外一轮脱敏与人工终审；"能启动"与"功能都正常"的验收范围必须在动工前钉死，否则会无限膨胀
