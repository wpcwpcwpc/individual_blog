## Context

站点现状：`src/pages/index.astro` 只有 hero（姓名 + `SITE.tagline`）与「精选项目 / 其他项目 / 文章」三段；`src/pages/about.astro` 三段散文；`src/pages/resume.astro` 是独立 HTML 文档，用 pdf.js 把 `public/resume/resume.pdf` 逐页画进 canvas。全站没有一处给出"我是谁、会什么、在哪个方向"的结构化信息。

两条既有约束与本变更直接冲突，必须先处理：

1. `RESUME.md` 写着"PDF 原件是唯一内容源；页面上不写死任何履历文本"。引入文本简历等于引入第二个内容源，该条款必须改写，否则两处数字迟早打架。
2. `add-personal-site` 的 `site-foundation` 规定内容不得出现时效性文案（"正在求职"等）。求职信号只能用常驻表述承载。

可复用的地基：content collection + frontmatter 校验、`scripts/sanitize-check.mjs` 脱敏闸门、`scripts/check-figures.mjs` 指标口径校验、`pdfjs-dist`（已在依赖里，简历页在用）。

## Goals / Non-Goals

**Goals:**

- 招聘方进站 10 秒内获得三件事：这人是谁、能力范围、怎么找到他
- 站点侧履历事实有唯一真源，首页身份区 / 技术栈 / 简历文本页从同一份数据渲染，不靠人工同步
- 简历文本版可复制、可被搜索引擎与 ATS 解析；PDF 保留为投递与打印形态
- 站内可实名雇主，与简历 PDF 口径一致；脱敏红线（内部产品名、项目代号、内网信息）不变
- 措辞 evergreen：不写"正在找工作"，用常驻的方向与可合作领域表述

**Non-Goals:**

- 不改 PDF 生成链路（`build-pdf.mjs` 管的是项目页导出，简历 PDF 仍由 `docx → pdf` 人工产出）
- 不做在线简历编辑器、不做后端表单收集投递
- 不重构站点骨架（不套用新的组件库、不改配色与排版规范本身，只新增两个区块的排版规则）
- 不在站内公开手机号

## Decisions

### 1. 站点侧真源为结构化数据文件，而非 Markdown 内容集合

新增 `src/data/profile.ts`，导出：`identity`（姓名、一句话定位、简介段落、所在地、工作年限口径）、`directions`（方向标签）、`stacks`（技术栈分组：组名 + 条目数组）、`experience`（经历条目：公司、职位、时间、要点）、`education`、`contact`。

首页身份区、技术栈区块、简历文本页三处都从这一份渲染。**替代方案**：放进 content collection 的 Markdown，正文自由写。放弃原因——Markdown 里同一件事在首页与简历页会被抄两遍，抄写即漂移；结构化数据让"首页只展示子集"成为 selector，而不是复制粘贴。

### 2. 简历文本版走 `/resume`，PDF 查看器让位到 `/resume/pdf`

`/resume` 从"PDF canvas 容器"改为文本简历：可选中、可复制、可被爬。现有 pdf.js 渲染实现**不删**，整体搬到 `/resume/pdf` 路由原样保留（pdf.js + 懒渲染 + 兜底阅读器都在，代码不动）。

**替代方案**：文本页开在 `/resume/text`，`/resume` 继续是 PDF。放弃原因——外部链接与导航指向的应是信息密度最高、最可读的形态；PDF canvas 是历史实现，不是最佳门面。两个页面互相链接，PDF 页顶部给"下载原件"。

### 3. `experience` 结构化到"要点级"，而非整段散文

经历条目拆成 `{ company, title, period, highlights[] }`，highlights 是一句话一条。首页身份区只用 `identity`（不列经历），简历文本页渲染完整结构。**替代方案**：`experience` 存一整块 Markdown。放弃原因——首页若哪天要抽一条经历作亮点，散文块抽不出来；且结构化后 `check-figures` 类校验才有抓手。

### 4. 双内容源的一致性靠"抽取 PDF 文本做断言"，不靠自律

`pdfjs-dist` 已在依赖里。新增 `scripts/check-resume-sync.mjs`：提取 `public/resume/resume.pdf` 的文本，断言站点侧关键事实在 PDF 文本中**都出现**——雇主名、学校、学位、时间区间（如 `2025.12`）、指标精确值（`19 个`、`30+`、`150+`、`170+`、`80%`、`2 pd` 等，清单从 `GLOSSARY.md` 第三节的"履历原文精确值"取或用导出常量）。缺失即构建失败并列出缺哪条。

方向是单向的（PDF ⊇ 站点侧事实，不做反向全等），因为站点侧刻意只写子集、且刻意用弹性区间。

**替代方案**：只在 `RESUME.md` 写一句"改简历记得两处同步"。放弃原因——这类人工约定在本仓库已被 `figures` 校验证明不可靠过一次。

### 5. 雇主实名：改词表，不改扫描器

`GLOSSARY.md` 第〇节已把"雇主公开名称"列为可公开，但 `GLOSSARY.local.md` + CI secret `GLOSSARY_WORDS` 里仍把雇主名当禁出词（现状是"站内不点名"）。本变更从两处词表移除雇主名，站点内容可直接实名。**扫描器实现与豁免机制一律不动**——它拦的是内部标识，不是公开身份。

站点侧另加一条自律：站内展示继续用弹性区间（十余个 / 数十个 / 百余条），精确值只出现在简历文本页与 PDF。两套口径在 `GLOSSARY.md` 第三节显式声明为"各自合法"，避免终审时被当成打架。

### 6. 首页信息量与区块顺序

区块顺序固定为：身份区（hero）→ 技术栈 → 精选项目 → 其他项目 → 文章 → 联系。身份区预算：一句话定位 + 简介 ≤ 3 句 + 方向标签 ≤ 4 个 + 入口链接 ≤ 3 个；技术栈 ≤ 5 组、每组 ≤ 6 条。超预算的细节一律进简历文本页。

**替代方案**：把技术栈放进 `/about`，首页只留入口。放弃原因——技术栈是招聘方的第一筛选项，藏在二级页等于没有。

## Risks / Trade-offs

- [PDF 与站点漂移] → `check-resume-sync.mjs` 进 `npm run build` 链，缺事实即构建失败；构建失败信息直接列出缺失条目，修复成本低于事后被发现
- [首页变长稀释项目展示] → 身份区与技术栈区有明确条目预算（决策 6），且技术栈用紧凑的 label + 条目排版，不用卡片阵列
- [实名后站点与 PDF 数字口径被指打架] → `GLOSSARY.md` 第三节显式登记"站内区间 / 简历精确值"为两个合法口径；同时 `check-figures` 继续保证站内区间与登记值逐字一致
- [改 `/resume` 语义影响既有外链] → PDF 形态未消失，仅路径变 `/resume/pdf`；`RESUME.md` 与导航同步更新，发布后 grep 站内是否有指向旧语义的文案
- [`profile.ts` 变成无人维护的死数据] → 它同时是首页与简历文本页的渲染源，两处都在线上可见，改动有即时反馈
- [ATS 解析 HTML 简历的效果不可控] → 保持语义化标签（`h2` 分节、`ul` 列条目），不把经历排版成 `<table>`；文本页同时提供 PDF 下载

## Open Questions

- 工作年限是否写进身份区（写"多年"这类区间，还是完全不提）？倾向用区间，避免时间点老化
- 首页联系区是否直接展示邮箱明文（现在是 `mailto:` 链接）？倾向保持明文，招聘方复制方便
