## Why

站点现在的门面是"知识分享站"：首页只有名字与一句 tagline，关于页三段话，`/resume` 只有一个 PDF canvas（文字不可复制、搜索引擎与招聘系统抓不到）。招聘方按链接进来，看不到"这人是谁、会什么、在哪个方向"，只能靠 PDF 里那两页纸。**站点的主用途是求职门面，知识分享是支撑证据，不是主角。**

同时简历目前是"改一次要动 PDF"的单轨交付：PDF 便于邮件投递与打印，却是站内最不可读的形态——不可选、不可检索、ATS 解析不到。两个场景需要两种形态，缺一不可。

## What Changes

- **首页身份区（hero）扩写**：一句话定位之外，补一段自我介绍（做什么、几年、在哪）、当前专注方向标签（Agent 工程 / Agent 评测与可观测 / AI 应用 / 测试开发与质量效能），以及常驻入口（看简历、看项目、邮件联系）
- **首页新增「技术栈」区块**：按能力分组列出（Agent/LLM 工程、Agent 评测与可观测、后端与服务、数据与客户端、工程方法），与简历口径同源
- **简历文本版页**：`/resume` 在 PDF 之外提供可复制、可索引的文本简历（同一份内容的 HTML 呈现），PDF 仍作为投递与打印形态保留
- **口径单一来源扩展**：技术栈条目、方向标签、履历事实与 `GLOSSARY.md` 第三节的指标登记对齐；文本简历里的精确值（19 个 Agent / 30+ 工具 / 150+ Spec Change 等）登记后与 PDF 同源，站点展示区仍用弹性区间
- **雇主实名**：站内不再回避雇主公开名称（网易、联想），与简历 PDF 一致；脱敏红线不变（内部产品名、项目代号、内网信息仍禁出）
- **措辞 evergreen**：不写"正在找工作"这类时效性文案，改为常驻的「方向」与「可合作领域」表述

## Capabilities

### New Capabilities

- `hire-profile`: 站点身份与能力展示——hero 简介、专注方向、技术栈分组、联系入口的内容结构与措辞约束（evergreen、口径同源、不含时效性文案）
- `resume-text`: 简历文本版——与 PDF 同源同口径的 HTML 简历，可复制、可被搜索引擎与 ATS 解析，且与 PDF 不一致时的以谁为准

### Modified Capabilities

- `site-foundation`: URL 拓扑契约补 `/resume`；首页区块顺序契约（身份 → 技术栈 → 精选项目 → 文章 → 联系），保证新增区块不打乱既有骨架
- `showcase-resume-handoff`: 简历交付形态从"PDF 单轨"改为"PDF + 文本版双轨"，文本版继承稳定路径要求；联系渠道边界扩展为站内身份区（仅邮箱与代码托管主页，手机号不上站）
- `sanitization-gate`: 雇主公开名称从禁出词表降级为可公开标识（与 `GLOSSARY.md` 第〇节口径一致），站内实名不触发闸门；同时登记文本简历引入的精确履历指标

## Impact

- 改动文件：`src/pages/index.astro`（hero 扩写 + 技术栈区块 + 联系区）、`src/pages/resume.astro`（双轨切换）、新增简历文本内容（content collection 或结构化数据源）、`src/site.config.ts`（tagline/描述/方向标签）、`src/styles/typography.css`（新块的排版规范）、`GLOSSARY.md` 第三节（登记文本简历精确值）、`RESUME.md`（"PDF 是唯一内容源"的条款必须改写，否则两处内容源冲突）
- 脱敏侧：`GLOSSARY.local.md` 与 CI secret `GLOSSARY_WORDS` 需同步移除雇主名（本地与 CI 必须同时改，否则本地假通过或 CI 假拦截）
- 风险一：双内容源漂移（PDF 与文本版数字打架）→ 由 `resume-text` 的"同源同口径"条款 + `figures` 校验约束
- 风险二：实名后站点与简历的泛化口径冲突（站内"十余个 Agent" vs PDF"19 个"）→ 需在 `GLOSSARY.md` 显式声明"站内展示用区间、简历用精确值"为各自合法口径
- 风险三：首页信息量上升稀释项目展示 → 身份区与技术栈区 MUST 控制在一屏可扫读的量级（措辞与排版的量级约束写入 `hire-profile`）
