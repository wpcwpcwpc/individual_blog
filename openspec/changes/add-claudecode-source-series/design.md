## Context

站点当前：14 个页面，内容集合只有 `projects`（1 篇真实项目 + 1 篇示例）与 `posts`（6 篇自撰文章 + 1 篇示例）。文章只有详情页 `/posts/<slug>`，没有列表页——首页把全部文章平铺出来，因此内容规模一涨就会失控。

待导入材料：一套自撰的 Claude Code CLI 源码拆解，位于公司侧文档目录，共 27 个带序号前缀的文件；其中 00–24 号段（23 篇，约 2.4 万行）是纯技术拆解，25–28 号段是公司内部工程内容（内部标识不入公开仓库，对照私有词表）。整套材料已有自带的阅读指南，并把它分成五个分区。

约束：站点侧内容一律过脱敏闸门（禁出词表 + `scripts/sanitize-check.mjs`）；URL 契约（`/projects/<slug>`）不得变更；引擎静态、零后端。

## Goals / Non-Goals

**Goals:**

- 让 23 篇长文成体系上站：有专区入口、有章节顺序与分区、有上一篇/下一篇导航
- 导入过程可复跑、可审计：来源边界写死在脚本里，不靠人记
- 文章模块恢复可扩展性：首页不再是无限列表，列表页支持分区与分页
- 清掉脚手架示例内容，站点只剩真实内容

**Non-Goals:**

- 不改写源文档正文（只做必要的内网标识改写与链接改写）
- 不导入 25–28 号段；不把源目录、源绝对路径写进仓库
- 不做全文搜索、阅读进度、评论、RSS、i18n
- 不动 `/projects/<slug>`、简历页、deck、既有 6 篇文章正文

## Decisions

**D1 专栏复用 `posts` 集合，而非新开集合。**
在 posts schema 上加 `series` 相关字段，章节详情仍走既有文章排版与闸门。
理由：新集合要复制布局、样式、闸门与查询逻辑，收益只是"语义干净"。
代价：posts 的语义变宽，分区规则必须集中在 `src/utils/content.ts`，否则散落成暗规则。

**D2 专栏元数据单点落在 `src/series.ts`。**
登记专栏 id、标题、描述、分区顺序与分区说明；专区页、列表页、章节页都读它。
理由：与 `src/site.config.ts` 同构（配置不写进内容，内容不写死配置）。
分区顺序沿用源文档自带阅读指南的五个分区，并前置一个「导读」分区安置 00 号阅读指南：导读 / 核心架构 / 工具与能力扩展 / Agent 核心系统 / 安全与可观测性 / 工程支撑。

**D3 章节 slug 用 `claudecode-<NN>-<english>`，映射表写在脚本里。**
如 `claudecode-03-query-engine`。号段保留源文档前缀，便于源/站对照；英文短名由脚本内的显式表给出，不从中文标题机器翻译。
理由：slug 是发布后的 URL 契约，一旦上线不得漂移；把映射固化在脚本里，重跑结果稳定。
代价：源文档新增/改名时需维护映射表——脚本对未映射的号段直接报错退出，不允许"猜一个 slug"。

**D4 导入是一次性动作，脚本常驻仓库。**
`npm run import:series -- --src <dir>`，只读源目录；产物写进 `src/content/posts/`；源文档本体不进仓库。
理由：站点是唯一真源，源目录只是输入；脚本保留是为了可复跑与可审计（改规则后重导）。
frontmatter 记录 `source`（仅文件名）与 `sourceSha256`（前 12 位），日后可判断源是否漂移，且不泄漏路径。

**D5 内网标识改写走脚本内的显式规则表，闸门做兜底。**
规则表覆盖扫描命中的几类：内网 IP → 「内网地址」、`localhost:<port>` → 「本地端口」、`C:\...` 本地路径 → 「本地路径」、`*.corp/.netease/.internal` 域名 → 「内部域名」、疑似工号数字 → 泛称。
理由：源文档不可改（公司侧），改写必须发生在导入这一步；改写不彻底时 `npm run sanitize` 硬拦构建，不会漏到线上。

**D6 章节互链改写为站内 URL，解析不了的降级为纯文本。**
`./NN-xxx.md` → `/claudecode/<slug>`；锚点 `#小节` 原样保留。指向已归档文档（源侧 `archive/` 里的 09/13/14 等）的引用 → 去掉链接只留文字，并打印告警清单。
理由：宁可少一个链接，也不能出一个死链；`npm run check`第二道保险。

**D7 文章列表分区 + 分页，首页只留入口。**
首页「文章」区 = 专栏卡片（含篇数与分区概览）+ 最近 5 篇单篇；新增 `/posts` 列表页按「专栏 / 单篇」分区，每页 10 篇。
理由：首页是门面不是索引；专栏与单篇混排会互相削弱。

**D8 章节元数据从源文档头部提取到 frontmatter。**
源文档开头的「阅读时长 / 重要程度 / 前置阅读」落在 frontmatter（`readingMinutes` / `weight` 等），正文保留原文块引用不动。
理由：专区页要按星级与时长排序展示，不能靠运行时解析正文。

**D9 清理示例内容后不补模板分支。**
首页「其他项目」区在无数据时已隐藏，删掉 `sample-project.md` 后自然消失；`sample-post.md` 同理。
理由：不留"空状态样板"，避免示例内容再次被当成示范。

## Risks / Trade-offs

- **内部内容误入** → 脚本用号段白名单（只收 00–24）+ 黑名单（25–28 命中即 `exit 1`）+ 导入产物过 `npm run sanitize`；三道都在构建前。
- **改写不彻底的内网标识** → 闸门硬拦（不是告警）；扫描已确认 00–24 只有零散 IP/端口/路径，量级可控。
- **slug 漂移导致外链失效** → 映射表固化 + 章节 slug 视同 URL 契约，只在专区内部引用，未对外发布前不需重定向。
- **构建体积与耗时上升**（新增 23 长文页） → 静态产物仍远小于一次图片站；构建时间以实测为准，若明显劣化再考虑分页构建优化。
- **内容合规**：拆解对象是闭源商业产品的内部实现（经源码阅读/反混淆），公开分析存在合规灰区 → 由作者确认后发布；`RELEASE-CHECKLIST.md` 增一条发布前确认项。
- **源文档日后更新** → 一次性导入会与源脱节；`sourceSha256` 让漂移可见，是否重导由作者决定。

## Migration Plan

1. 脚本 + schema + 专区页 + 列表页落地，示例内容删除
2. 本地 `npm run build`（四道闸门 + 链接检查）与 390px 视口核对
3. push → CI 自动部署（GitHub Actions，单通道）
4. 回滚：删导入产物与新增页面 → revert 提交；上线前未对外发布过章节链接，无需重定向
