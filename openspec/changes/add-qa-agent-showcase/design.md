## Context

- 需求背景见 `proposal.md`：为 QA Agent 平台构建对外展示内容，落地在个人站点上
- 地基由 `add-personal-site` 提供（Astro 站点、排版规范、脱敏闸门、图表管线、Cloudflare Pages 部署），本变更只做内容
- 探索阶段的关键发现：
  - **口径不一致**：Agent 目录文件数、注册数与既有内部文档宣称数三处不同 → 必须冻结单一来源
  - **现成图表素材可参考但不可用**：内部仓库已有若干 Mermaid 图源（架构、路由、评测流程），是很好的图意来源，但全部需脱敏重绘
  - **最强差异化素材是变更记录**：内部仓库有上百条 spec-driven 变更记录，这是"我用工程方法管住了一个复杂系统的演化"的直接证据，deck 装不下，文章能装下
- 约束：NDA 红线（内容重写、图重绘、指标区间化）；站点内容 evergreen；雇主仓库零留痕

## Goals / Non-Goals

**Goals:**

- 3 分钟可信：项目页读完即建立"系统真实存在、规模可信、角色清晰"的判断
- 深挖钩子：对愿意深看的人提供取舍层面的叙述（为什么这么做，放弃了什么）
- 口径单一来源：全站涉及的数字与命名只来自一处登记，改一处全站同步
- 图表一次绘制复用三处：站点文章 / deck / PDF
- 分期可交付：先上项目页 + 2 篇文章即可对外可用，其余增量补

**Non-Goals:**

- 交互式架构图（点击节点看详情）——后续演进
- 完整功能清单或 API 文档搬运（这是对外展示，不是运维手册）
- 包含任何真实业务代码、真实截图、内部指标精确值
- 英文版 / 多语言
- 时效性文案（"正在求职"之类）

## Decisions

### D1 叙事分层：三种粒度对应三种读者

| 读者行为 | 入口 | 内容形态 | 目标 |
|---|---|---|---|
| 扫一眼（<1 分钟） | 项目页首屏 | 一句话定位 + 架构总览图 + 3 个关键数字 | 判断"值得点" |
| 认真看（3~5 分钟） | 项目页全文 | 问题 → 五层架构 → 我的角色 → 结果 | 建立可信度 |
| 深挖（>10 分钟） | 文章系列 | 取舍与教训（为什么这么选、放弃了什么） | 产生深挖欲望 |

理由：不同读者投入意愿差异大，用同一形态同时满足会导致"扫读嫌长、深挖嫌浅"。

### D2 口径冻结为单一来源

- 在 `GLOSSARY.md` 之外新增一处**对外口径登记**（放在项目页 frontmatter 的 `figures` 字段或独立 `showcase-figures.md`），登记：Agent 数量、工具数量、流程层数、指标区间表述
- 全站所有出现处 SHALL 引用同一登记值
- **Agent 数量以代码注册数为准**（注册在 `_register_builtins()` 中的条目数），而非目录文件数或旧文档数字；对外表述留弹性（如"十余个专职 Agent"）以避免版本漂移
- 每个数字登记时附带"来源说明"（一句话说明这个数字怎么来的），便于自我复核与应对追问

### D3 项目页结构（`/projects/qa-agent`）

```
① 一句话定位        它是什么、解决谁的什么问题
② 问题背景          3 个痛点，每个一行
③ 架构总览          五层架构图（宽图，可缩放查看）
④ 分层要点          每层 3~5 条，配小图
⑤ 取舍与难点        2~3 个真实取舍（与文章互链）
⑥ 我的角色与边界    做了什么、没做什么（诚实边界 > 夸大）
⑦ 结果与指标        区间化表述，标注"指标已脱敏"
⑧ 深挖入口          文章索引 + deck + PDF 下载
```

### D4 文章分期与选题优先级

- **第一批（首发必须）**：
  1. **用 spec-driven 流程管理多 Agent 系统的演化**——差异化最强，别人复制不了
  2. **为什么拆成多个专职 Agent 而不是一个大 Agent**——最常被追问的架构题
- **第二批**：双向 MCP 桥接取舍 / 三道闸门 / 上下文工程 / 评测与口径统一
- 每篇文章 SHALL 至少包含一个"我放弃了什么"的取舍段落——这是区分"做过"与"想清楚"的地方
- 文章与项目页双向互链：项目页第 ⑤ 段链到相关文章，文章末尾链回项目页

### D5 概览 deck（`/deck/qa-agent`）

- 约 12 页：封面 → 问题 → 架构总览 → Agent 编排 → 工具与 MCP → 管控与安全 → 上下文 → 评测 → 可观测 → 工程方法 → 结果与角色 → 联系
- 形态：由 Slidev 构建为静态产物，拷入站点公开子目录（`/deck/qa-agent/`），与站点零耦合（站点不依赖 Slidev 运行时）
- **共用图源**：deck 用图直接取 `diagrams/` 产出的 SVG，MUST NOT 单独维护一套图
- 排版沿用站点规范的等效约束（字号下限、每页要点 ≤5、无真实代码）
- deck 是"锦上添花"：deck 缺失或构建失败 MUST NOT 阻塞项目页与文章发布

### D6 内容侧脱敏

- 扩充 `GLOSSARY.md`：
  - **泛化映射表**：内部系统/平台/产品 → 对外泛称（如设备农场平台、服务管理 CLI、协作单系统、配置表仓库）
  - **禁出词表**：精确词 + 正则（公司名、产品名、游戏名、内部域名、内部端口、工单系统、真实文件路径、人员标识）
  - **指标区间化登记**：每个对外指标项一行，登记其区间或倍数表述
- `SHOTS.md` 维护需要真实截图的位置：编号 / 页面 / 标题 / 取景建议 / 脱敏注意 / 覆盖状态
- 项目页与文章中的所有图 SHALL 为对外重绘版本（依据 `diagram-pipeline` 规格）
- 发布前自检清单：口径一致性、禁出词零命中、指标全区间化、图无内部代号、SHOTS 状态与页面一致

### D7 简历交付（`showcase-resume-handoff`）

- 简历正文一行链接指向 `/projects/qa-agent`（稳定路径，见地基的 URL 契约）
- 纸质版简历附二维码指向同一 URL（生成方式在实施时定，产物入仓库）
- PDF 作为兜底：邮件附件场景可发 PDF；PDF 链接失效时不影响主链接可用
- 联系渠道边界：只放邮箱等可公开渠道，MUST NOT 放手机号、内网 IM 账号

## Risks / Trade-offs

- **[R1] 脱敏漏网（NDA 红线）** → 构建前置硬拦截 + 内容侧自检清单 + 人工终审三道；图全部重绘不复制
- **[R2] 数字对不上（面试被追问）** → D2 单一来源 + 每条附来源说明 + 对外表述留弹性区间
- **[R3] 内容量过大烂尾** → 分期（首发只要求项目页 + 2 篇），每篇文章独立可交付
- **[R4] 项目页写成功能清单（无差异化）** → 结构里强制"取舍"与"角色边界"两段；每篇文章强制一个取舍段落
- **[R5] deck 与站点图不同步** → deck 取同一批 SVG，禁止单独维护
- **[R6] 内容过时（系统继续演进）** → 内容写"架构与思路"而非"当前功能列表"；数字用弹性表述，降低维护频率
- **[R7] 被同事或雇主看到引发问题** → 内容不含内部信息（已由闸门保证）；表达聚焦工程方法与个人贡献，不做产品宣传

## Open Questions

- 项目页是否需要"演进时间线"（用变更记录的时间分布重绘，脱敏后可读性不错）——倾向要，是差异化素材
- 文章系列是否同步发到技术社区引流（在同一批内容上改写成平台稿）——不属本期范围，可后续定
- 是否需要英文摘要（面向外企或海外机会）——后续可定
- 二维码生成方式（本地脚本 vs 在线服务）——实施时定，注意不得把真实数据发往第三方服务
