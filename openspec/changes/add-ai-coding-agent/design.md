## Context

被替换的 Agent 是「脚本工坊」：六阶段状态机（澄清 → 方案 → 积木匹配 → 探索 → 生成 → 调试）驱动，六道阻塞审批门把关，产出目标仓库里的用例文件。它的骨架里通用部分（探索、改代码、跑命令、人工把关）占比很大，业务部分（状态机、游戏内执行、用例登记、仓库规则注入）把通用部分锁死在了内部环境。

本次改造的判据只有一条：**这个能力离开内部环境还成立吗？** 成立则保留并通用化，不成立则剥离。

## Decisions

### D1 去掉状态机，改用「任务清单 + 审批门」驱动

六阶段状态机的价值在于约束一个多轮、多产物的固定流程；通用编码任务的流程并不固定。因此删除 `case_phase / case_requirement / case_plan / case_block_findings / case_exploration_notes / case_file / case_debug_iterations` 的推进逻辑，改由：

- 任务清单（`task_list` / `task_update`）承载多步任务的进度可见性
- 审批门承载「动手前的关键决策点」：非平凡改动先提方案

代价是失去阶段级强制约束（旧版「未批准不得进 P3」的硬闸门）。取舍理由：硬闸门只对固定流程有意义，通用编码里强推阶段反而会逼出无效的形式化步骤。审批门保留了真正重要的那部分——**改动前必须有人点头**。

### D2 工具面按「只读直通 / 副作用审批」分层

| 层 | 工具 | 理由 |
|---|---|---|
| 只读直通 | `file_read` `grep` `glob_search` | 零副作用，逐次审批只会拖慢节奏 |
| 命令（安全面） | `bash` `wait` | 框架自带系统级黑名单与命令分类 |
| 命令（破坏面） | `run_command`（审批） | 不可逆动作必须有人点头 |
| 写盘 | `write_file` `edit_file`（均审批） | 写盘是本 Agent 唯一能改变仓库状态的动作 |
| 决策 | `request_approval`（审批） | 方案 / 选型确认 |
| 澄清 | `ask_user` `get_user_input` | 信息收集，零副作用 |

拒绝「所有 bash 都审批」的方案：逐条确认会让正常编码节奏碎掉，而框架已有的命令分类 + 危险模式拦截已经能覆盖「悄悄干坏事」的主要路径。

### D3 审批工具新建，不与工坊工具复用

`tools/coding_tools.py` 独立承载本 Agent 的审批工具，不走 `tools/case_studio_tools.py`：

- 后者的 `request_approval` 把 kind 限死在 `plan / new_block_design`（业务语义），且同文件里全是目标仓库相关的实现（白名单、REPL、语义库、知识条目）
- 本 Agent 通过 `AgentDefinition.extra_tools` 装配工具，**不**注册进 `api/server.py` 的内置工具表——避免把游戏侧路由与全局工具注册表卷进本次改动，改动面收敛到三个新文件加一行注册

### D4 危险命令双层拦截

单靠「提示词要求模型自己判断」不够，加一层确定性的工具调用层拦截：

1. **硬拦**：`coding_guard_hook` 作为 `agent_tool_hooks` 挂在调用链上，`bash` 命中不可逆模式（递归删除、盘符格式化、强推、硬重置、清空工作树、整表删除、发布、递归改权限等）时不执行，返回改用审批通道的指引
2. **人工兜底**：`run_command` 是这类命令的唯一出口，每次都弹审批卡，携带 `purpose`（这条命令要干什么）

两层叠加后，绕过路径只剩「换个说法但语义不变」——这类变形由审批卡的 `command` 全文呈现覆盖，人工可判。

### D5 编辑能力委托，不复制校验链

`edit_file` 内部委托既有 `file_edit` 工具的入口函数，保留它的完整校验链（改前必读、外部改动过期检测、多重匹配拒绝、`old_string` 精确性提示）。理由：把 120 行校验逻辑抄一份到审批工具里，等价于埋一处长期分叉；委托的代价只是多一次 `getattr` 取入口，且取不到时明确报错而非静默落盘。

### D6 依赖切断清单

| 切断项 | 原用途 | 理由 |
|---|---|---|
| 仓库规则文件注入 | 目标仓库的 `.mdc` 规则 | 内部仓库布局专属 |
| 代码图谱服务 | 符号级探索 | 内部服务，需内部 token |
| 配置表 RAG | 查内部配表真值 | 业务数据 |
| SVN 信息工具 | 推导仓库路径 | 内部版本控制布局 |
| 工坊 skill 目录 | 工作流与积木速查 | 业务工作流 |
| MCP 工具注入 | 游戏调试 MCP | 内部运行时 |
| 历史记忆注入 | 内部执行历史库 | 业务数据 |

保留 `find_skill` / `load_skill`：仓库内既有 skill 仍可被发现和加载，属于通用能力而非业务绑定。

### D7 与既有游戏侧资产共存

`api/case_studio_*.py`（工坊路由）、`tools/case_studio_tools.py` 其余工具、`session_state.case_*` 字段、`.claude/skills/case-studio` 本次不动——它们被其它路由与前端页面引用，清理属于独立变更。副作用是 `hooks/mcp_safety_hook.py` 里的 `CaseStudioAgent` 工具白名单条目变为死键（该文件按 agent 名查表，不存在的 agent 不匹配即放行），无害，清理另立项。

### D8 待作者确认：镜像区「只删不创」口径

`GLOSSARY.md` 第〇节把镜像区处置记为「只删不创、不上站」，本次属受控加法（新增三个文件）。规格层面 `source-sanitization` 允许 `REPLACE` 类受控加法，但仓库口径表尚未同步。处理方式：tasks 5.3 记录为待确认项，先按作者指示落地代码，口径同步与否由作者决定。

## Risks

- **运行时不可本地验证**：本机无 Agno 依赖，验证只能到语法与结构层（tasks 5.4 如实登记未覆盖范围）
- **委托取入口的耦合**：`edit_file` 依赖 Agno `Function.entrypoint` 属性；该属性在本仓已被 MCP 工具包装层使用（`tools/lazy_mcp_tool.py`），属既有约定，但仍属框架内部细节，取不到时报错而非降级写入
- **审批 kind 语义收窄**：`request_approval` 的 kind 从业务语义（`new_block_design`）换为通用语义（`plan` / `design`），旧 kind 不再接受，避免两套语义混用
