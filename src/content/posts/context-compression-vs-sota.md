Agent 的上下文有一组互相冲突的约束，任何压缩方案都是在这三角里做取舍：

1. **成本与延迟** —— 输入 token 按量计费，prefill 时间随长度线性上涨
2. **前缀缓存** —— 推理侧的缓存按**字节级前缀**命中，改一个字符，后面的全废
3. **保真度** —— 压掉的信息，Agent 永远找不回来；找不回来就会编

检索时代的老经验（"旧东西存进向量库，要用再捞"）只解决第一条，同时会炸掉另外两条。
这是下面所有坑的总根源。

先说结论：**压缩是最后手段，不是默认动作；而任何不谈缓存账的压缩方案，等于没算过总账。**

## 一、四层防御

四层机制挂在 Agent 运行生命周期的四个不同位置，各自管一段：

| 层 | 机制 | 触发时机 | 粒度 |
|---|---|---|---|
| **L0 源头预截断** | 每个工具自带输出上限：读文件、命令输出、等待结果、代码检索、协调者回传各有自己的截断线 | 每次工具调用 | 字符级 |
| **L1 历史窗口** | 只回灌最近若干轮对话（keep-recent-N），对深度追问场景收得更紧 | 每次调用前回灌 | 轮次级 |
| **L2 轮内压缩** | 未压缩的工具结果累计到窗口一成左右时触发；另有总上下文安全网兜底 | 工具调用之间 | 消息级 |
| **L4 跨会话蒸馏** | 软/硬阈值 → 结构化条目 → 向量库；下一会话以提醒形式注入恢复 | 每轮结束 | 会话级 |

外加两个辅助机制：

- **收益递减检测**：连续三轮增量低于阈值，判定"继续做也没有产出"，主动收尾而不是把预算烧干
- **缓存意识**：高频追问场景关掉会话摘要——见第四节的第一个坑

层间职责是**刻意划开**的：

- L1 管跨轮的历史量，L2 管当前轮内的工具结果，L4 负责归档但**不截断当前会话**
- **L0 优于 L2**：能在源头截断，就绝不事后压缩（代价账见 4.3）

## 二、被忽略的一极：前缀缓存

推理侧的缓存机制很朴素：同模型同租户下，**完全相同的 token 前缀序列**只算一次 prefill，KV 张量直接复用。
关键是"字节级精确匹配"——从第 0 个 token 开始连续不变的那一段才算命中。

实测下来，单个长任务里**九成以上的输入 token 走的是缓存命中**。这个比例意味着：

- 压缩的本质是**原地改写历史** → 压缩点之后的前缀全部失效，后续每次调用都要重新 prefill 那一段
- 而压缩本身还要付一次模型调用（压缩器也是模型）

所以这两件事是**对冲关系**：省下的 token 和断掉的缓存，得放在同一个账本里算。
把压缩当"纯赚"的方案，多数在真实账单上并不赚。

## 三、和业内方案逐项对账

把 2025–2026 的主流做法拆成五类，逐项对照自己这套实现：

### 3.1 分层防御（预算 + 微压缩 + 自动摘要）

- **是什么**：预算控制管"花多少"，微压缩管"实时清"，自动压缩管"深度摘要"。精神与内存管理的缓存分层同构
- **怎么做**：任务开始前给各段（指令 / 历史 / 工具结果 / 输出预留）分配配额；上下文到六成左右时**不调模型**，用规则把过期的工具调用与结果剥成一行占位符、掩掉过时的思考块；到八成半左右再触发模型深度摘要，重写旧对话
- **效果**：公开研究结论是"微压缩 + 摘要"组合的成本效益优于纯滑动窗口，且能避免上下文触顶时**突然崩溃**（旧窗口方案超限瞬间全丢）

### 3.2 小模型 token 剪枝

- **是什么**：把压缩器从"完整模型调用"降级成"小模型逐 token 二分类"
- **怎么做**：蒸馏一个 BERT 级小模型，对每个 token 预测"是否影响最终输出"，删掉低信息量的；query 感知变体会用当前问题引导注意力，重点保头部与尾部、削中间（长 prompt 的中段最容易被忽略）
- **效果**：论文报告最高 20 倍压缩率、性能损失极小；检索场景省约七成半 token 成本。**推理路径完全不碰目标模型**

### 3.3 失败驱动的压缩策略优化

- **是什么**：把"怎么压"从静态提示词升级成可学习对象
- **怎么做**：收集失败案例，把失败归因到"压缩丢了某类信息"，反推出自然语言规则（例如"某类日志里的端口行必须保留"），迭代优化规则集合，再蒸馏进新提示词
- **效果**：论文报告在 95% 以上任务准确率下，上下文用量降 26%–54%。落地成本高（需要失败信号闭环），属研究前沿

### 3.4 驱逐 + 外置记忆

- **是什么**：长会话不再塞满窗口，旧状态"驱逐"到外部存储，需要时检索回灌
- **怎么做**：轮次结束把状态向量化落外库；下轮组装时按相似度取回若干条，窗口内只留近期
- **效果**：理论上会话长度不受窗口限制；代价是**检索质量直接决定保真度**，漏检就是幻觉源

### 3.5 学习"何时压缩"

- **是什么**：把"何时压"从硬编码阈值升级为学习问题
- **怎么做**：以"压缩后完成率 + token 成本"为奖励，用强化学习训练触发策略
- **效果**：论文报告长程任务完成率提升、成本下降；工业界落地少，阈值法已覆盖绝大多数场景

### 3.6 对账结果

| 业内技术 | 本系统对应 | 状态 | 评估 |
|---|---|---|---|
| 分层防御（预算 + 微压缩 + 自动摘要） | L0/L1/L2/L4 四层 | ✅ 结构对齐且更细分 | 多出 L0 源头截断与收益递减检测 |
| 跨轮保留最近 N 轮 | L1 历史窗口 | ✅ 有 | 只用了轮次级旋钮，消息级与"限制历史工具对数"两个旋钮未用 |
| 微压缩（规则剥离、零模型调用） | 仅 L0 固定截断 | ⚠️ 部分 | **最大差距**：L2 触发时逐条调模型，成本有尖峰；业界剥过期工具对是零成本 |
| 小模型 token 剪枝 | 无 | ❌ 缺 | 压缩器全靠模型调用，成本高一个量级 |
| 失败驱动策略优化 | 静态提示词 | ❌ 缺 | 无学习回路；研究前沿，投入产出比低 |
| 学习压缩时机 | 固定阈值 | ❌ 缺 | 硬编码；但按量触发已比框架默认的次数触发精细 |
| 驱逐 + 外置记忆 | L4 → 向量库 + 提醒恢复 | ✅ **优势项** | 正是业界范式；结构化条目（未完成步骤优先）+ 恢复点，比"只存摘要"更工程化 |
| 缓存意识 | 缓存账 + 禁令体系 | ✅ **超出业界平均** | 多数框架根本没把缓存纳入压缩权衡 |
| 蒸馏保真 | 粗截断 | ⚠️ 粗 | 超限直接丢，业界用分段摘要 |
| 增量压缩 | 全量重蒸馏 | ⚠️ | 有重复成本 |

**总评：架构中上，执行引擎偏贵。** 骨架完整，三个设计点超过一般实现（按量触发有实测调参、缓存与压缩的权衡意识、L4 归档不截断的职责分离）；
短板集中在执行层——全系统只有"贵模型"这一级成本阶梯，没有零成本路径与小模型路径；压缩无保新策略；蒸馏是粗截断。

## 四、五个踩过的坑

### 4.1 会话摘要每轮更新，把缓存打断了

**坑**：框架会在每轮结束时更新会话摘要，并把它注入指令段尾部。
指令段尾部字节每轮都在变 → 从摘要位置开始，每轮请求的缓存**全部落空**。

**解法**：在高频追问场景显式关掉会话摘要——历史窗口已覆盖常规追问深度，摘要是冗余的，而且断缓存。

**教训：压缩与记忆类特性不是免费加成，每加一个都要过一遍缓存断点账。**

### 4.2 只重写了同步入口，异步路径上是死代码

**坑**：压缩判定最初只重写了同步方法。
但运行时全部走异步链路，而框架基类的异步版本**是同步逻辑的复制粘贴，并不委托给同步方法**。
结果：按量触发的判定在生产上是**死代码**，压缩只靠总上下文安全网兜底。
日志证据很干脆：每次模型调用都在压缩，却没有一条"命中判定"的记录。

**解法**：同步与异步两个入口都重写，共享同一个判定函数。

**教训：继承第三方框架时，sync/async 双入口不委托是常见陷阱；重写必须成对。**
这件事后来写进了实现类的文档注释里，警告下一个改动者。

### 4.3 调低阈值的诱惑

**坑**：把压缩阈值调低，token 就省得更多？不是。
压缩是原地改写历史——每次压缩，**压缩点之后的缓存全断**，后续每次调用都要重新 prefill 这段，还要额外付压缩器的一次调用。
阈值取"窗口的一成左右"是算了**双面账**之后的平衡点。

**解法**：方向反转——**靠源头截断控制体积，优于事后压缩**。
读文件走定向切片而不是整文件回传，代码检索、知识库、等待类工具各自压到自己的上限。

**教训：调低阈值之前，先算缓存断点账。**

### 4.4 为什么按 token 量触发，而不是按调用次数

**背景**：框架默认的触发条件是"累计若干次工具调用就压"，比如三次。
但工具谱系是**两极分化**的：有的工具返回一行 `OK`（几十 token），有的返回大段检索结果（上万 token）。
按次数触发，前者会被无谓地反复压缩，后者迟迟压不下去。

**决策**：改成按数据量触发——只统计未压缩的工具结果消息，累计到窗口一成左右才压。
换算下来，一次大范围代码检索抵得上几十次小工具调用，压缩只发生在真正积累起来的时候。
判定失败时**诚实禁用压缩**（而不是静默退回框架默认的次数语义），避免"压了但不知道为什么压"。

### 4.5 蒸馏截断，丢的恰恰是最该保的

**坑**：蒸馏时把历史拼成文本，整体截到万级字符、单条截到千级字符再送模型。
长会话里**早期的关键线索**（根因判断、已确认的结论）可能没进蒸馏就被丢了——
而这些恰恰是集体经验里最该沉淀下来的东西。

**现状**：仍是粗截断，与业界的分段摘要（map-reduce）有差距，列在下一节 P2。

## 五、固化成的缓存禁令

踩过多次之后，把"怎么组装上下文"变成了纪律，逐条写成禁令：

1. ⛔ 指令段里禁止出现时间戳、动态变量、随机 ID —— 动态内容放到消息级后缀
2. ⛔ 裁剪窗口时禁止把指令段挪离首条消息
3. ⛔ 禁止把可变状态整体 dump 进指令段
4. ⛔ 指令文本禁止引用会被插值的变量
5. **组装铁律：静态前置、动态后置** —— 分叉点越靠后，可复用的前缀越长

前四条都是同一条原理的具体化：**指令段必须是字节稳定的**。第五条规定它稳定到哪一段为止。

## 六、下一步：按性价比排的路线

### P0 压缩保最近若干条原文（消息级）

- **做法**：压缩触发时，把最后若干条未压缩的工具结果**排除在压缩集之外**，只压旧的
- **依据**：刚产出的工具结果是当前推理步的直接依赖，压掉它等于让 Agent 失明；这正是业界微压缩的同款策略
- **代价**：缓存断点仍在（压缩点之后照样失效），保新策略换的是保真度，不是缓存

### P1 规则剥离层（轮内零模型压缩）

- **做法**：触发时先走规则——超龄的已完成工具对（调用 + 结果），把结果替换成一行占位文本（工具名 + 一句摘要），跳过模型；模型摘要只留给"真的大"且"真的新"的结果
- **依据**：工具谱系两极分化，规则剥离先把"小而过期"的批量清掉，模型只处理长尾；公开研究也支持"微压缩 + 摘要"的组合优于任一单层。预期轮内模型调用可降一半以上
- **代价**：占位策略需要调参，丢太狠会幻觉 —— 一行摘要是不破的保真底线

### P2 蒸馏改分段摘要（map-reduce）

- **做法**：超限的历史先切块、逐块摘要、合并后再蒸馏，单条截断同步放宽
- **依据**：消除 4.5 的"早期信息未蒸馏即丢弃"
- **代价**：多若干次小模型调用，换长会话零信息丢失

### P3 压缩槽换小模型剪枝

- **做法**：压缩环节后接小模型剪枝端点，替换逐条模型摘要
- **依据**：单条压缩成本可降一个量级（20 倍级 vs 摘要的 3 倍级）
- **前置**：需要网关支持或本地部署小模型；**建议 P1 做完再评估** —— 规则剥离之后，剩余需要模型压缩的量可能已不值得上重武器

### 明确不做（写明理由）

| 项 | 理由 |
|---|---|
| 失败驱动的压缩策略优化 | 需要失败信号标注闭环，当前量级投入产出比低；但其思路可以低成本借鉴——在 P2 的提示词里手工预置领域规则（如"某类启动日志的端口行必留"） |
| 强化学习决定压缩时机 | 阈值法已覆盖绝大多数场景，收益递减检测已提供兜底；等 P0–P2 落地后看 token 曲线再定 |
| 框架自带的历史工具对裁剪旋钮 | 零成本旋钮，**顺手项**：在历史窗口层挂一档，与轮内压缩解耦；先小流量验证保真度影响 |

### 收敛判据

每步落地后看三个数，**三数不恶化才进下一步**：

- 净输入 token 增量（剔除缓存命中部分）
- 压缩环节的模型调用次数
- 任务完成率回归

## 附：术语速查

| 术语 | 一句话 |
|---|---|
| prefill / KV cache | 首次计算注意力的 K/V；同前缀复用 KV 即可跳过 prefill |
| middle loss | 长 prompt 的中段信息易被忽略，压缩需要 query 感知 |
| compact | 把旧历史重写为摘要替换原文（原地替换） |
| eviction | 旧状态逐出到外部存储，按需检索回灌 |
| map-reduce 摘要 | 分段摘要再合并，避免单次截断丢信息 |
| 占位符剥离 | 工具结果替换为一行占位文本，零模型成本 |
| diminishing returns | 连续轮次增量低于阈值，判定继续无产出 |
