做 Agent 系统一年下来，让我花最多时间的不是崩溃，是**不崩**。

崩溃会给你堆栈和行号。静默故障只给你一句"看起来正常"：调用返回了、进程活着、
日志里没有 ERROR，但事情一步都没做，或者做了别的事。
我把遇到的这一类整理成几组形态，以及事后沉淀下来的判断习惯。

## 一、零耗时"成功"加零副作用

最典型的一次：一个委派动作立即返回"成功"，耗时短到不真实，被委派的 Agent 从头到尾没运行过。
原因是寻址用的是它的**展示名**，而框架内部把展示名做了一层规范化——查不到就跳过，
不报错、不告警，安静地什么都不做。

后来同类现象又出现过几种：异步包装里塞进去的其实是个协程函数，
调用返回了一个对象然后被丢弃，函数体一次没执行，异常还被降级成 warning；
外部工具的子进程拿到了句柄却忘了真正分发，于是所有子命令都是"空输出 + 退出码 0"。

**判断习惯**：不要用"调用有没有返回"验证有副作用的行为，
要用**副作用本身**验证——事件计数、落库记录、文件变更、下游状态。
凡耗时短得不合理，先怀疑什么都没发生。
零耗时"成功" + 零副作用，是静默故障最可靠的签名。

## 二、一个同步调用，让整个服务被当成挂掉

单进程单事件循环的服务里，一个同步网络调用就能把整条队列堵住。
健康检查排不到调度，于是探测超时，于是被判定不健康，于是被自动重启。
外部看到的现象是**连接失败**——和真实原因隔了四层，几乎没人会第一时间往那个方向查。

更隐蔽的变体是把长等待藏在拦截层里：某个前置检查里做了一轮轮询，
这期间事件循环被占住，流式输出一片空白，只有心跳在保活。
功能没坏，界面也没报错，用户只看到"卡住了"。

**判断习惯**：症状出现在最外层时，先问"它依赖的资源有没有在排队"。
任何阻塞式 I/O 都要追问一句：**谁会因为等它而排不到队**。
长等待还要放在**可观测**的位置——如果一段等待期间用户看不到任何进展，
那它无论多合理都是错的，因为没法判断是在工作还是死了。

## 三、能力即意图：权限别只写在提示词里

给一个 Agent 开放了通用执行能力之后，"工具白名单"就形同虚设——
它可以直接绕过去打底层接口。更糟的是提示词里当时还写了正确的调用格式，
等于把绕过方法一并教给了它。

另一类错是**注册不等于可调用**：工具注册表决定它"能看见什么"，
权限表决定它"被允许调用什么"。只做前者的系统，权限实际是敞开的，
因为注册通常由业务配置驱动，没有人为权限负责。

**判断习惯**：模型不会区分"我有能力"和"我被允许"。
管控必须落在调用现场（这部分展开见[三道闸门](/posts/three-guardrails)）。
还有一条容易忽略：**别在提示词里写绕过示例**，模型会照做。

## 四、谁说了算：状态与真相源

这类坑的共同点是"两个地方都觉得自己是对的"。

- **网络失败不等于操作没生效**。请求可能已经到达并被处理，只是响应在回来的路上丢了。
  凭"没收到响应"就本地回滚，会把已经生效的服务端改动二次覆盖。解法是幂等键：
  同一个请求标识重复到达时返回上次结果，而不是再执行一次。
- **瞬态通知不能当真相源**。通过广播告知"数据变了"，如果消费方在广播窗口里掉线，
  它会永远不知道自己错过了什么。真相要在**主动拉取时校验**（比对版本），不匹配就重新同步。
- **终态不能交给模型**。流程的结束信号如果依赖模型主动调一个上报工具，
  它总有一次会把总结当成终态、或者轮次耗尽直接停下。决定流程走向的状态，
  必须由代码兜底探测一次。
- **单调计数器要问"重启后怎样"**。进程内的序号重启即归零，
  消费方按只增不减的规则过滤，就会把新事件当成旧的丢掉。
  而且同一个变量同时当"去重标记"和"断点续传位置"时，迟早互相矛盾——
  这两个语义需要各自的归属。

**判断习惯**：任何状态都先问"谁是唯一真相"，再问"它重启、掉线、并发时分别怎样"。
答案里出现"应该会"的地方，就是下一次静默故障的位置。

## 五、看起来在动，其实没动

对接外部可执行程序或第三方服务时，文档描述的能力边界经常和实际不符：
接口声称能查到结果，实际那个字段从不返回；某个操作声称可以后台运行，
实际窗口一最小化整条服务就卡死；失败之后声称会恢复，实际永久卡在中间态。

还有一类是**平台假设会变**：依赖的某个系统命令行工具在新版本系统里被移除了，
脚本从此安静地失败（连报错文本都是旧的）。

**判断习惯**：外部依赖先写一个最小脚本实测能力边界，再定设计——文档只作参考。
另外，如果工具层把"退出码"归一成了人话文案，那判断依据就只剩**文本**：
按返回文本而不是退出码做失败分类，反而更可靠。

## 六、几个可以照抄的习惯

- 断言副作用，不断言返回。
- 耗时异常短或异常整齐，先怀疑没执行。
- 系统提示必须逐字节稳定：任何会变化的内容注入进去，都会让缓存失效、成本失真。
- 给通用执行能力 = 白名单失效，必须补内容级审查。
- 网络失败 ≠ 未生效；瞬态广播 ≠ 真相。
- 流程终态由代码兜底，模型只负责表达。
- 外部依赖先实测，再设计；文档只作参考。

## 最后：记录坑的机制，比坑本身重要

上面每一条我都写过文档，但真正让它们没被重复踩的是**记录方式**：

- **按现象开头**，保留原始报错文本。查的时候人只会记得"当时报了句什么"，不会记得编号。
- **收编有标准**：静默失败、根因可迁移、违反直觉、有线上后果——收；
  设计阶段的"风险预判"不收，因为它没发生过，混进来只会让手册变成设计文档副本。
- **编号要有门禁**。我早期的记录靠人工在文件末尾追加编号，
  结果两个并行的工作各自以为下一个号是自己的，出现了重号，修订历史也乱了。
  编号和版本这类元数据是需要规则的资产，不是随手写的东西。

分工也该分清：**规则文档回答"必须怎么做"，记录回答"为什么会有一条这样的规则"**。
两处都写全文，一定会分叉。所以我把已经固化成硬约束的内容只留指针，
案例留在记录里——需要的人顺着指针能看到约束，写约束的人也能回来看到事故现场。
