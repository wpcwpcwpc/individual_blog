Agent 的能力边界，取决于它能调用什么。把外部能力接进来有两种方向：
**向外**接入外部能力（客户端、设备、服务），**向内**把平台能力暴露出去供别人调用。
两个方向我都做了，也都踩过坑。

## 方向一：外部能力按需拉起，而不是常驻

![双向能力桥接](diagram:arch-mcp-bridge)

最省事的做法是让所有能力常驻：进程起来、工具注册好，Agent 随时可用。
我放弃了，原因是**"注册了"不等于"能用"**：

- 常驻进程吃掉的是每一台机器的固定资源，哪怕一天只用一次
- 进程崩了不会有人知道，工具还在工具列表里，模型调用时才发现连不上
- 更糟的是假可用：会话启动时探活一次通过，跑到一半服务挂了，
  错误出现在业务步骤里，排查成本远高于"启动时就告诉我不可用"

所以我改成四步：**列清单 → 按需拉起 → 就绪探活 → 工具注入**。
只有探活通过的能力才进入 Agent 的工具列表。
再配一个后台健康检查：连续几次探活失败就重连，
让"已连接"这个状态始终对应**真实可用**，而不是一次性的启动结果。

## 方向二：把平台能力反向暴露出去

反向这一层看起来是"多做事"，收益却很直接：**平台能力不再只被自己的界面消费**。
别的系统想用同一个能力，不需要复制一套实现、也不需要适配我的内部接口。
代价是接口一旦对外，就变成了承诺：改行为要考虑调用方，
这又反过来要求自己的行为定义得足够稳定——
这件事和"规格先行"的工程流程是同一件事的两面。

## 取舍：我放弃了"简单"，换来了三层复杂度

**放弃一：一个统一的常驻连接池。**
换来的是状态机：能力有"未拉起、拉起中、就绪、失联"四种状态，
每种状态的超时、重试、降级都要定义。这部分代码不出现在任何演示里，但它是可用性的地基。

**放弃二：让模型自己重试。**
一开始我想把"连不上就再试一次"交给模型判断，后来放弃了：
模型会重试到耗尽预算，还常常对着已经死掉的服务反复尝试。
改成**探活失败即拒绝注入该能力**——模型看不到不可用的工具，就不会去调它。
让"不可能发生的事"在工具列表层面消失，比在提示词里叮嘱它"不要调用失败的服务"有效得多。

**放弃三：把外部协议细节暴露到 Agent 定义里。**
Agent 定义只声明"我需要哪类能力"，不关心它背后是本地进程还是远端服务。
这层间接让能力可以替换实现而不动 Agent——代价是多了一层映射要维护。

## 什么时候不该双向

如果只是内部自用、能力数量稳定、调用方只有自家前端，
反向暴露那层可以先不做：它是给"别人要用"准备的，没有调用方时只是负担。
按需拉起则建议保留——**假可用**这一类故障的代价，比多写一个状态机高得多。
