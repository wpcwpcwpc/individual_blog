把功能都塞进一个大 Agent，看起来最省事：不用设计交接、不用维护注册表、
不用解释"为什么这件事归它管"。我最后放弃了这条路，理由不是设计品味，而是四个具体成本。

## 一个全能 Agent 会遇到什么

假设一个 Agent 承担从规划到出报告的完整链路，它需要几十个工具。
问题从第一轮对话就开始：

- **选择面变大**：每次调用，模型都要在几十个工具里选一个。工具越多，
  选错的概率越高，而错误往往不是"报错"，是"用错了但跑通了"
- **上下文被挤占**：工具描述是要占 token 的。无关工具常驻上下文，
  真正影响判断的信息（历史结论、当前约束）反而被挤出去
- **权限无法收敛**：读日志的步骤与改文件的步骤，一旦在同一个 Agent 里，
  它们就共享同一套权限。想只给前者开只读权限，做不到
- **模型选型被迫折中**：同一条链路里既有需要强推理的判断，也有机械的搬运。
  用一个模型跑全部，要么为搬运付贵模型的费用，要么让判断环节吃亏

前三条是同一个根因：**工具集不收敛，权限与上下文就没法收敛**。

## 拆分判据：四条同时成立才拆

我不是按"功能模块"拆 Agent 的，那样会拆出十几个职责重叠的 Agent。判据是这四条：

1. **工具集可枚举且互不重叠**：一个 Agent 的工具集能收敛到个位数，且与其它 Agent 不大量交叉
2. **权限级别一致**：整个 Agent 内的操作风险等级相同，不需要为了一个高危动作放宽整组权限
3. **输入输出可交接**：它需要的输入能从上一步的产物里拿，它的输出能以文件或状态提交
4. **有独立的失败语义**：它失败之后，"重试它"和"跳过它继续"是两种明确的选择

四条同时成立，拆才有收益；只要有一条不成立，拆出来的就是"多一个需要维护的部件"。

## 拆开之后，链路上多了什么

![任务路由分发](diagram:flow-routing)

- 一条指令先经意图判别分流：不同意图进不同链路，而不是所有任务都过同一个大 Agent
- 每个 Agent 有独立定义：角色说明、工具白名单、权限级别、上下文注入策略
- Agent 之间**不直接对话**，通过共享状态与产物交接——任何一步失败都能定位到具体环节
- 模型按槽位路由：编排用低成本模型、推理用强推理模型、图像理解用多模态模型

![Agent 编排与模型槽位](diagram:arch-agent-layer)

最后一条是我最满意的部分：拆分之后，模型选型从"一个折中"变成"每环各取所需"，
省下的不只是钱，还有等待时间。

## 取舍：我放弃了"一个 Agent 搞定"和"每步都拆一个"

**放弃一：一个 Agent + 几十个工具。**
代价我认：编排层因此变复杂。多了路由、多了交接协议、
多了"为什么这件事归它管"的解释成本，调试时还要先定位是哪一环出的问题。
换来的是权限可收敛、上下文干净、模型各取所需——这三样是**架构属性**，
一旦定了很难在后期补上，而编排复杂度是可以逐步消化的工程问题。

**放弃二：按步骤逐粒拆分。**
一度想把每个动作都拆成独立 Agent，好处是职责极简。
放弃了，因为拆分有固定的交接成本：每次交接都要定义产物格式、
失败语义与重试策略。步骤拆得越细，系统里"胶水"越多，
到最后没人能说清一次任务到底经过几环。
我最后停在十余个 Agent：**每个 Agent 都对应一类工作，
而不是对应一个步骤**。

**没放弃的一件事：失败可见。**
拆分的最大风险是错误被吞在交接处——上一步悄悄失败，下一步拿着空数据继续跑。
所以我把"每一步的状态写回共享状态"变成硬约束：
链路可以中断、可以恢复，但不存在"凭空继续"。

## 什么时候不该拆

任务形态单一、工具集天然收敛在个位数、权限只有一种——这时单 Agent 更简单也更快。
拆分不是先进，它只是解决**工具集与权限无法收敛**这个特定问题的手段。
先看问题，再决定要不要用它。
