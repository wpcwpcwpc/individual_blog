系统上线那天不是终点，而是一连串"再改一点"的开始。
本文讲我怎么让一个持续膨胀的多 Agent 系统，在积累了一百余条变更记录之后仍然自洽。

## 为什么多 Agent 系统的演化格外难

普通服务的复杂度大多落在代码里：函数在哪、谁调谁，读代码就能还原。
多 Agent 系统有一半复杂度落在**看不到的地方**：

- **约定**：什么任务该派给谁、哪一步允许并行、失败后谁来收尾，这些不在任何函数签名里
- **口径**：同一个能力，在注册表、文档、汇报材料里可能是三个数字
- **边界**：哪些工具对哪个 Agent 可见、哪一步必须人工审批，散落在配置与钩子里

这三样东西的共同点是：**它们只有被写下来才存在**。
靠记忆维护，结果就是新加一个 Agent 时，作者只能凭感觉猜前人的约定；
猜错了不会报错，只会让行为悄悄跑偏——这正是多 Agent 系统最贵的一类故障。

## 我用的流程：提案 → 设计 → 任务 → 规格 → 实现 → 验收 → 归档

![工程流程](diagram:flow-spec-process)

每一次改动（新能力、修缺陷、重构，一律平等）都走同一串工件，缺一步不进实现：

- **提案**：先写清"为什么做、改什么、影响谁"，一句话说不清的改动不准开工
- **设计**：把关键决策与放弃的方案写下来，含"不做什么"
- **任务**：拆成可勾选的小块，每块能在一次工作内完成——小块才可验收
- **规格**：把行为写成"当…时，系统应当…"，这是后续验收的唯一依据
- **实现**：按任务推进，边实现边回填事实；发现设计与现实不符，回头改设计而不是改规格
- **验收与归档**：逐条对照规格自检，通过后并入基线，成为下一次改动的参照

它带来的三件事，恰好对应上面三个难点：

1. **口径单一来源**。凡是量化事实只在登记处定义一次，页面与材料从登记处取值；
   我还加了一道构建期校验——两处数字不一致，构建直接失败。数字打架不再靠人细心。
2. **并行不打架**。多人同时改同一模块时，冲突在规格层就暴露：两个提案动同一段行为、
   对"什么算通过"理解不一致，此时返工只损失文档，不是代码。
3. **验收有依据**。"我觉得好了"不算完成，规格逐条对过才算——
   对一个有上百条历史变更的系统，这条规则让回归成本从"重新理解意图"降为"跑一遍清单"。

## 取舍：流程确实吃掉一部分编码时间

最诚实的反对意见是：**你花在写文档上的时间，本可以用来多写两个功能。**

我承认这是真的，而且短期看不划算。一次改动如果只是加一个判断分支，
走完整流程（提案 + 规格 + 任务 + 验收）可能比直接改代码多花一倍时间。
我仍然坚持这么做，是因为收益的结算周期比成本长：
在改动量累积到某个量级之后，"能不能讲清为什么"决定了系统还能不能继续改。

但流程本身也会腐化——**规格不更新，流程就退化成摆设**，
甚至更糟：它给人"有文档"的安全感，而文档是过期的。
所以我把"实现中发现事实变化就回填规格"写进了流程本身，
并把"规格与实现不符"当作缺陷处理，而不是当作文档维护工作。

另一个取舍是**放弃了"一次做对"的幻想**。
规格允许修改——但必须留下修改痕迹与理由，而不是悄悄改掉。
这条规则让历史看起来不那么漂亮（能看到自己反复），却让后来的每次决策都有据可查。

## 什么样的项目不该这么干

- 一次性原型、明确要丢掉的实验代码：把流程压到只留"设计"一段就够
- 单人维护、生命周期短于三个月的脚本：规格的价值还没结算，系统就该退役了

流程是给"要活很久、还会被别人接手"的系统准备的。
如果一个系统注定只活一次，写规格是在给将死的房子精装修。

## 这套流程在这个项目上跑出了什么

四十余项能力规格、百余条变更记录，全部可追溯到"为什么做"与"怎么验收"；
新同学接手时不需要读代码去猜约定，读规格即可。
