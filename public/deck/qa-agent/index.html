面向游戏 QA 的多 Agent 编排平台

把一句自然语言任务交给一群专职 Agent，从用例生成一路跑到回归报告

文棚嶒 · 786939553@qq.com · github.com/wpcwpcpc

02 / 12

问题背景

一轮版本回归的链路太长，人被迫当调度器

  • 链路长：起客户端、切版本分支、改配置、跑用例、收日志、写报告，每一步都要人串起来
  • 现场还原难：失败信息散落在客户端日志、服务端日志与用例三处，每次都要重新拼现场
  • 经验留不下来：判断依据留在人的记忆里，下一个版本没人知道上次为什么这么判

03 / 12

架构总览

自上而下是调用关系，自下而上是反馈关系

  • 接口层建会话，编排层判定链路，Agent 层装配工具与管控钩子
  • 每一步的产物都写回共享状态，成为下一步或下一轮的输入

04 / 12

Agent 编排

  • 专职化让每个 Agent 的工具集收敛到个位数，而不是几十个工具里挑一个
  • 协调者负责拆解与派发，工作池负责受限并发：能并行的并行，共享资源串行
  • 模型按槽位路由：编排用低成本模型、推理用强推理模型、图像理解用多模态模型
  • Agent 之间不直接对话，通过共享状态与产物交接——任一步失败都能定位到环节

05 / 12

工具与外部集成

  • 方向一：能力按需拉起，就绪探活通过后才注入工具——避免"工具在但服务没起来"的假可用
  • 方向二：平台能力反向暴露为标准协议服务，供其它系统调用
  • 后台健康检查让"已连接"始终对应真实可用，而不是一次性的启动结果
  • 技能库把"某类任务怎么做"沉淀成可复用资产，改流程不用发版

06 / 12

管控与安全

  • 约束写进代码而不是提示词：确定性、不占上下文 token、还可在评测里衡量
  • 拦截不是报错，而是带引导的拒绝——回传"应该怎么做"，让模型自己纠正
  • 工具白名单两层：注册层决定看得见，调用层决定能调用；只做前者权限实际是敞开的
  • 不可逆动作（改文件、执行代码）暂停等人审批，写操作限制在授权目录内

07 / 12

上下文工程

  • 压缩是最后手段不是默认动作：未超阈值保持原文，避免把细节摘成正确的废话
  • 红线条目（权限边界、必须遵守的输出格式、判定依据）不进压缩器，永远原样保留
  • 阈值不靠拍脑袋：把上下文用量当观测项，用真实运行数据反推区间
  • 结论沉淀成条目、下一轮按需检索回填，长时任务才能连续跑下去

08 / 12

评测体系

  • 评测与生产解耦：冻结输入、隔离环境，不产生任何真实副作用
  • 三层指标：确定性门禁 → 检查点覆盖 → 轨迹指标；能确定性判的绝不交给模型判
  • 模糊判定带交给裁判模型，裁判本身要先用人工判过的样本校准
  • 方差是一等指标：变化量小于基线波动一律判为噪声，不发布"提升"结论

09 / 12

可观测

  • 会话事件流、工具调用日志、状态变更记录——排障与评测取材共用同一份数据
  • 长链路任务异常从"翻日志定位"降到"面板分钟级定位"
  • Token 消耗与上下文占用全程可视，成本与稳定性都可解释

10 / 12

工程方法

  • 每次改动都走同一串工件，缺一步不进实现；规格是验收的唯一依据
  • 口径单一来源：量化事实只登记一处，页面取值由构建期校验强制一致
  • 并行不冲突：多人改同一模块时，冲突在规格层暴露，而不是在代码里互相覆盖
  • 代价是纪律：规格不更新，流程就退化成摆设
